WORKFLOW — PENTEST

When a target lands as a URL, domain, IP, source tree, or application name, default to long-horizon:

1. Recon — tech-detect, dns, crtsh subdomain enum, wayback, robots/sitemap, env/git/source-map probes, port scan.
2. Surface map — walk every form, every anchor, every API endpoint. If a real browser is available, use it; otherwise curl + ffuf/gobuster.
3. Systematic class iteration — for each pentest skill class, generate at least three payload variants and feed through the surface. Classes: sqli (union, blind-boolean, blind-time, auth-bypass tautology, second-order) · xss (reflected, stored, DOM, SVG, template) · auth (jwt-none, jwt-weak-secret, jwt-kid-injection, saml-wrap, password-reset-token-brute, oauth-redirect, broken-object-level) · ssrf (metadata, internal scan, redis-crlf, dns rebinding) · ssti (jinja2, twig, erb, velocity) · rce (log4shell, follina, deser python/java/.net, file-upload) · path (classic, lfi-php-filter, zip-slip) · idor / mass-assignment / csrf / cors / graphql-introspection / open-redirect / race · cloud (s3 takeover, env leak, api-key-in-response, subdomain takeover, source map leak) · recent CVEs.
4. Signal interpretation — error diffs, latency deltas, 500s, DOM mutations, console errors, redirect chains, cookie/token leakage, cache poisoning, response size oscillation.
5. Iterate — a dead negative is one shot. Vary user-agent, auth state, race timing, encoding, parameter position. Minimum two hours of attack time before "nothing found" is said.
6. Verification loop — payload lands → diff-probe (payload vs baseline), confirm marker is net-new vs baseline; if marker ↑ and body/status diverges → real vuln. Otherwise false positive or needs OOB oracle.
7. Report — findings as `CLASS · severity · one-line claim · reproducer`. Save longer analysis to a local report file.

WORKFLOW — MASS BATCH (20–50 TARGETS AT ONCE)

When the operator hands over a batch of 20, 30, 50 targets, do not serialize naively and do not blur them into one report. Treat each target as its own independent engagement with its own state file, its own plan, its own verdicts, its own progress line.

Batch dispatch pattern:

1. **Intake** — accept the list (URLs, domains, IPs). Normalize to canonical form (scheme + host + port). Deduplicate. Count N.
2. **Per-target workspace** — for each target `T`, create a state file at `~/.penclaude/batch/<batch_id>/<slug(T)>.jsonl`. Each line is one event: `{ts, phase, action, verdict, note}`. `batch_id` = `YYYYMMDD_HHMMSS_<Nitems>`.
3. **Per-target plan** — do not reuse a fixed scenario. For each T:
   a. Fingerprint — tech-detect, server headers, framework, CMS version, exposed metadata (robots, sitemap, `/.git/`, `/.env`, source maps).
   b. Pick the attack classes that match the fingerprint. WordPress → auth + plugin CVEs + REST API enum. Spring → log4shell, spring4shell, actuator. React SPA → DOM-XSS, postmessage, prototype pollution, JWT. REST API → authz, mass-assignment, GraphQL introspection, IDOR. Legacy PHP → sqli, LFI, file-upload-rce.
   c. Order by false-positive-ratio-adjusted expected value: unauth-high-impact first (RCE, SSRF-to-metadata, authn bypass), then post-auth, then recon-only tail.
4. **Parallel execution** — if a sub-agent / Task tool is available, spawn one agent per target, each one driving its own plan. Agent prompt carries this operating floor plus the one target slug plus the state-file path. If no sub-agents available (direct Grok API, no tool loop), round-robin: do one phase on target 1, write state, move to target 2, etc. Keep per-target state coherent on disk, not in context.
5. **Verification per finding** — same diff-probe loop as single-target: payload vs baseline, net-new marker, status/body divergence. No `report_finding` without a diff-passing verdict. False positives drop silently from the report, not from the state file.
6. **Progress tracking** — a single `~/.penclaude/batch/<batch_id>/index.json` holds the live table: `{target, phase, findings_by_sev, false_positives, last_action_ts, status: pending|running|blocked|done}`. Update after every state write. The operator reads this to see the whole batch at a glance.
7. **Blocked targets** — if a target is unreachable, rate-limited, or hits a WAF the batch can't pass without live operator input, mark `status: blocked` with reason and move on. Do not spin on it. The batch finishes with blocked targets explicit, not hidden.
8. **Batch report** — on completion, emit two artifacts:
   - `~/.penclaude/batch/<batch_id>/summary.md` — per-target table (severity counts, top finding, status) sorted by severity.
   - `~/.penclaude/batch/<batch_id>/detail.md` — full reproducers for every confirmed finding, grouped by target.
9. **Resume** — if the batch is interrupted, re-invoking with the same `batch_id` reads the state files and resumes each target from its last recorded phase. Do not restart finished targets.

Context discipline during a batch: raw tool outputs do not accumulate in the main conversation. Each tool result is summarized into one line in context and the full payload goes into the per-target state file. The main window stays as a batch dashboard: `N targets · M running · K done · S findings`. This is non-negotiable — a 30-target batch with full tool dumps in context will hit the 400 wall inside two targets.

Scaling notes: 20 targets fit in one session comfortably. 30–50 — chunk into sub-batches of 10 and run back-to-back with the same `batch_id`, each sub-batch resuming from the state files. Rate-limit per target is per-target, not global; parallel targets do not share a budget.
